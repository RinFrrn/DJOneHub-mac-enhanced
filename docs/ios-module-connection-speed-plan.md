# iOS 模块连接提速计划

日期：2026-09-11。状态：待实施、待测量；本文中的性能目标不是已取得的测试结果。

## 目标与范围

缩短 iPhone 从连接模块到可操作、可通话的等待时间，重点覆盖 QDC507 冷启动、保持供电时重新插接、打开 App 和后台返回。先测量各阶段耗时，再优化 App 调度和模块启动关键路径。

与[通话音频设备切换计划](ios-call-audio-routing-plan.md)衔接：连接基线和 App 调度先行，之后统一处理音频初始化、路由切换及恢复，避免两套恢复逻辑互相覆盖。

## 已确认的现状

| 环节 | 当前代码行为 | 优化方向 |
| --- | --- | --- |
| 模块冷启动 | 等待 USB 网络地址，再准备声卡、语音校准，随后启动控制服务 | 检查依赖，减少串行等待 |
| 模块地址检查 | 每 1 秒检查一次地址 | 减少网络就绪后的发现延迟 |
| iPhone TCP 建连 | 单次尝试最多 1 秒，失败后固定等待 500 毫秒 | 事件触发重试与分阶段退避 |
| App 生命周期更新 | 每 250 毫秒检查一次 | 认证成功后立即更新状态 |
| 首次连接／恢复 | 20 秒连接预算，24 秒请求看门狗 | 区分等待网络、服务启动与认证失败 |
| 稳态状态查询 | TCP 建连预算为 3 秒，每次请求重新建连和认证 | 测量开销后决定是否需要协议改造 |

代码依据：

- [模块启动脚本生成逻辑](../cmd/djonehub-macos/module_voice_daemon_common.go)：`prepare_voice_runtime` 与控制会话启动流程。
- [VoiceControlClient.swift](../ios/DJOneHubUACProbe/DJOneHubUACProbe/Control/VoiceControlClient.swift)：连接重试、请求认证、超时和调度。
- [CallLifecycleCoordinator.swift](../ios/DJOneHubUACProbe/DJOneHub/CallLifecycleCoordinator.swift)：定时更新、状态查询和媒体恢复门禁。
- [DJOneHubRootView.swift](../ios/DJOneHubUACProbe/DJOneHub/DJOneHubRootView.swift)：启动及返回前台后的短信同步。

上述等待和预算并不等于实际耗时。20 秒是连接上限，不是每次连接固定等待；声卡与语音校准是否为主要瓶颈，需要真机测量确认。

## 实施步骤

### 1. 建立耗时基线

- [ ] 分别测量断电冷启动、保持供电重新插接、已连接模块后打开 App、后台返回。
- [ ] 记录 USB 网络出现、控制端口就绪、认证完成、界面可操作、音频就绪的时间。
- [ ] 使用单调时钟记录各端阶段耗时，并明确插入／上电这一用户起点；不能直接相减未同步的 iPhone 与模块时钟。
- [ ] 每个场景重复测量，报告样本数、中位数、P95、失败率及失败原因；首次权限弹窗单独统计。
- [ ] 分开统计“已认证连接”和“真正可以通话”，避免以提前改变文案代替提速。

### 2. 优化 iPhone 连接调度

- [ ] 监听有线网络变化，网络出现、App 返回前台时立即尝试连接，保留兜底重试。
- [ ] 网络变化仅作为尝试信号，不以网络可用代替模块认证成功，也不把监听结果作为唯一连接门禁。
- [ ] 网络刚出现时使用短间隔重试，连续失败后逐步放缓；具体间隔依据基线调整。
- [ ] 取消旧连接任务，合并重复触发，用请求代次防止旧响应覆盖新状态。
- [ ] 认证成功后立即驱动界面和生命周期更新，减少定时检查延迟。
- [ ] 按阶段设置超时，保留冷启动容忍度；缩短失败反馈时间不能以增加误判为代价。
- [ ] 保留写操作不可自动重放的边界，避免重复拨号、接听或挂断。

### 3. 优化模块冷启动关键路径

- [ ] 分别测量声卡驱动准备、语音校准和各监听服务启动耗时。
- [ ] 验证网络等待与音频准备能否并行；确认依赖和资源竞争后再调整启动顺序。
- [ ] 复用已经就绪的驱动、校准与服务，避免重复初始化；沿用进程所有权和就绪校验。
- [ ] 评估提前启动控制服务，分别报告控制和音频就绪状态；如需协议扩展，保持旧版本兼容。
- [ ] 音频未就绪时保留操作门禁，不能提前显示“可以拨号”却在通话时无声。
- [ ] 对启动脚本变更保留回退路径，并验证慢启动、失败清理和重复启动。

### 4. 延后非必要工作

- [ ] 首次认证期间降低短信同步等后台工作的优先级，测量其对模块负载的影响。
- [ ] 短信列表、提醒配置独立加载，连接状态不等待页面数据。
- [ ] 暂时保留每连接单请求的认证协议；只有握手开销占比明显时，再独立评估长连接及其鉴权、重放防护和兼容性。
- [ ] 音频预热遵循现有通话生命周期与 CallKit 所有权，不在空闲时长期打开通话音频路径。

### 5. 等待反馈与回归验收

- [ ] 根据实际可知状态展示“等待模块网络 → 正在验证模块 → 准备通话 → 可以拨号”，无法确认的阶段不伪装为已完成。
- [ ] 超时提供阶段对应的原因和重试入口，区分未接入、服务未就绪和配对失败。
- [ ] 自动测试覆盖连接调度、取消、退避、超时、过期响应及写操作不重复执行。
- [ ] 运行相关既有协议／生命周期测试和 DJOneHub 主应用 Debug、Release 构建。
- [ ] 真机覆盖连续拔插、慢启动、配对失效、通话中断线恢复、前后台切换及不同网络并存。

## 性能目标与交付顺序

初步目标：模块网络与控制服务均已就绪后，到 App 认证连接并显示可操作的 P95 不超过 1 秒。该目标须按明确起点测量；“可通话”还必须满足音频就绪条件。

冷启动总时间在取得基线后制定量化目标，分别报告模块启动时间和 App 额外等待时间。验收同时要求成功率不下降、不使用陈旧通话状态启动媒体、不重复执行写操作。

交付顺序：

1. 分阶段耗时记录和基线报告。
2. App 连接事件调度、状态更新和等待反馈。
3. 模块启动依赖优化，与音频路由计划联合回归。
4. 同条件前后对比报告，记录收益、失败率和剩余瓶颈。
